# Calendar Waitlist Auto-Fill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Phase 1 of the Google Calendar cancellation waitlist auto-fill SaaS: detect cancellations via polling, match against a per-business waitlist, notify in batches by email + WhatsApp deep link, and let clients confirm into a replacement booking — all on free-tier infrastructure.

**Architecture:** Next.js App Router on Vercel (Node runtime), Supabase Postgres + Auth, an external 5-minute scheduler hitting `/api/cron/poll`, a `CalendarProvider` interface with a single `GoogleCalendarProvider` implementation, and Resend for email. Pure logic (matching, crypto, tokens) is zero-I/O and unit-tested; routes and cron orchestration are integration-tested against local Supabase with a fake `CalendarProvider`.

**Tech Stack:** TypeScript (strict), Next.js (App Router), Supabase (`@supabase/supabase-js`, `@supabase/ssr`), `googleapis`, `resend`, `zod`, Vitest, Supabase CLI (local dev + integration tests).

## Global Constraints

- TypeScript strict mode everywhere; no `any` without justification.
- All API routes run on the Node.js runtime (default for App Router) — never Edge — because `googleapis` and `node:crypto` require Node APIs.
- No Google Calendar push webhooks — polling only, via `updatedMin` incremental sync.
- No monetization tiers/billing in Phase 1 — no `tier` column, no gating.
- No automated browser/E2E tests this phase — Vitest unit + integration only; UI features get a manual walkthrough.
- Replacement Calendar events are plain events with no attendee invite.
- Only the business's dedicated bookings calendar is ever polled or written to — never primary/personal calendars.
- `min_confirm_lead_hours < min_notice_hours` must be enforced wherever either is set (migration CHECK constraint + dashboard form validation).
- Defaults: `batch_size = 3`, `batch_interval_minutes = 30`, `min_notice_hours = 24`, `min_confirm_lead_hours = 12` — all business-configurable.
- Waitlist entry expiry: 14 days from creation while `active`. (`pending_verification` status retired by Task 25 — per-entry verification replaced by account-level verification in `client_profiles`.)
- `google_refresh_token` is encrypted at rest with application-level AES-256-GCM; the key lives only in an environment variable, never the database; never logged; never sent to the client.
- Real secrets are entered by the user, not pasted into chat — every task that needs a secret states the env var name and leaves the value to the user via `.env.local` (gitignored).
- Per the user's standing instruction: implementation execution (subagent-driven or inline) does not begin until the user has been explicitly notified that it's starting.
